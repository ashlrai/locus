Use case · agencies and contractors

One laptop,
many client tenants.

A contract firm should never run one mega-MCP holding every client account. Locus runs one pin, one catalog: enter the client, do the work, leave with nothing residual.

Install Locus Firm mode doc →
What you get

  • Bindings per engagement. A binding is principal × tenant × provider accounts × CredentialRefs × policy, stored as TOML with no raw secrets.

    docs/firm-mode.md

  • Sealed sessions. locus enter acme seals the session with an HMAC pin to exactly one binding; tools succeed only while that seal is valid.

    crates/locus-core/src/seal.rsAGENTS.md · invariants

  • Full + read-only pairs. The firm-mode pattern is acme for day-to-day write work and acme-ro with read_only = true for audits, each pinned on demand.

    docs/firm-mode.mdexamples/agency-starter/

  • Workspace allowlist. A repo's .locus.toml allowed_bindings blocks wrong-tenant pins in that directory; --force overrides are audited.

    AGENTS.md · invariantsexamples/workspace.locus.toml

  • Dual control on destructive tools. Policy rules like "*.delete*" → dual_control hold a call until two externally authenticated identities approve.

    docs/policy.md

  • Reachability red-team. eval/env-reachability/redteam.py checks which ambient credentials a child process can still reach after a pin, with fake canaries and a throwaway HOME.

    eval/env-reachability/redteam.py
The loop
zsh · client work 
locus enter acme        # seal to the acme binding
locus whoami          # tenant + providers, no secrets
# ... agent session, scoped to acme only ...
locus leave           # no residual identity for the next client
locus enter acme-ro     # read-only surface for the audit pass
